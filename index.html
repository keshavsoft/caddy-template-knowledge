🧠 The Cold-Start Mental Model

Whenever you log into your VPS to host a new application (like appointment-notifier), you don't want to decipher Caddy's entire source code. You only need to answer two simple questions:

1. What port is free on the server?
Use npx caddy-cli -p to list every currently occupied port. Pick a free port (e.g. 3000).
2. What kind of traffic does my app generate?
Does it run HTTP and WebSockets on one port? Or does WebSocket run on a separate port? Or is it pure static HTML/CSS files?

Once you know the answer to Question 2, you simply generate the corresponding template with caddy-template and paste it into Caddy's route table.

⚡ Template 1: proxy (Unified HTTP & WebSocket)

Pattern: Unified Reverse Proxy npx caddy-template proxy appointment.keshavsoft.com 3000

The Scenario: Most modern Node.js applications (such as appointment-notifier) attach WebSocket servers (like ws or socket.io) directly to the existing Node HTTP server instance on port 3000.

Browser (HTTPS / WSS) ──:443──► Caddy Reverse Proxy ──:3000──► Node.js (Express + WebSocket Server) (Auto HTTPS & WS Upgrade)

Why Caddy Does This Automatically

In older web servers (like Apache or older Nginx), you had to manually set headers like Upgrade $http_upgrade and Connection "upgrade". Caddy handles WebSocket upgrading natively. If a client sends an HTTP Upgrade: websocket request, Caddy automatically transparently tunnels the TCP connection to localhost:3000 without any special flags!

Caddy JSON Route Block 
{
  "match": [
    {
      "host": [
        "appointment.keshavsoft.com"
      ]
    }
  ],
  "handle": [
    {
      "handler": "subroute",
      "routes": [
        {
          "handle": [
            {
              "handler": "reverse_proxy",
              "upstreams": [
                {
                  "dial": "localhost:3000"
                }
              ]
            }
          ]
        }
      ]
    }
  ],
  "terminal": true
}

🔀 Template 2: ws-split (Dual-Target Split Proxy)

Pattern: Path-Based Split npx caddy-template ws-split quotation.keshavsoft.com 9011 8080

The Scenario: Your architecture runs two independent services behind one subdomain:

  • Service A: Express REST API / HTML pages running on localhost:9011.
  • Service B: Standalone WebSocket server running on localhost:8080.
Browser Request ──► Caddy ──┬── /ws or /ws/* ──────────────► localhost:8080 (WS Server) └── All other paths (*) ────────► localhost:9011 (Web/API Server)

How Caddy Evaluates the Split

Inside the subroute, Caddy evaluates sub-rules in sequence:

  1. Route 0 (Specific Match): Checks if the request path is /ws or begins with /ws/*. If yes, it proxies to localhost:8080.
  2. Route 1 (Catch-All Fallback): Has no path filter, so all regular web/API traffic falls through to localhost:9011.
Caddy JSON Route Block 
{
  "match": [
    {
      "host": [
        "quotation.keshavsoft.com"
      ]
    }
  ],
  "handle": [
    {
      "handler": "subroute",
      "routes": [
        {
          "match": [
            {
              "path": [
                "/ws",
                "/ws/*"
              ]
            }
          ],
          "handle": [
            {
              "handler": "reverse_proxy",
              "upstreams": [
                {
                  "dial": "localhost:8080"
                }
              ]
            }
          ]
        },
        {
          "handle": [
            {
              "handler": "reverse_proxy",
              "upstreams": [
                {
                  "dial": "localhost:9011"
                }
              ]
            }
          ]
        }
      ]
    }
  ],
  "terminal": true
}

📁 Template 3: static (File Server)

Pattern: Static File Server npx caddy-template static cli.keshavsoft.com /usr/share/caddy

The Scenario: Serving client-side single page apps (SPAs), generated HTML documentation (like this handbook!), or static download assets directly from the VPS disk without running a Node.js process.

Browser ──:443──► Caddy ──► Local Filesystem (/usr/share/cli.keshavsoft.com) (Blazing-fast zero-copy file serving with ETag & Gzip)

Why vars.root is Required

In Caddy JSON, the file_server handler does not take a directory path directly. Instead, Caddy uses a dedicated vars handler to set the internal root variable first, which file_server reads:

Caddy JSON Route Block 
{
  "match": [
    {
      "host": [
        "cli.keshavsoft.com"
      ]
    }
  ],
  "handle": [
    {
      "handler": "subroute",
      "routes": [
        {
          "handle": [
            {
              "handler": "vars",
              "root": "/usr/share/caddy"
            },
            {
              "handler": "file_server"
            }
          ]
        }
      ]
    }
  ],
  "terminal": true
}

🌐 Template 4: multi-host (Domain Aliases)

Pattern: Multi-Host Binding npx caddy-template multi-host keshavsoft.com,www.keshavsoft.com 9328

The Scenario: You want both your root domain (keshavsoft.com) and its www alias (www.keshavsoft.com) to transparently route to the same application port (9328).

Caddy JSON Route Block 
{
  "match": [
    {
      "host": [
        "keshavsoft.com",
        "www.keshavsoft.com"
      ]
    }
  ],
  "handle": [
    {
      "handler": "subroute",
      "routes": [
        {
          "handle": [
            {
              "handler": "reverse_proxy",
              "upstreams": [
                {
                  "dial": "localhost:9328"
                }
              ]
            }
          ]
        }
      ]
    }
  ],
  "terminal": true
}

🔍 Caddy JSON Anatomy: Plain-English Field Reference

Every field in a Caddy JSON route block has a specific, critical purpose:

JSON Property What It Means Why It Matters
match[].host Array of domain names that trigger this route Caddy automatically requests and renews Let's Encrypt / ZeroSSL TLS certificates for every host listed here!
handler: "subroute" Creates an isolated routing context for this domain Keeps rules for one domain completely separated from all other domains on the server.
handler: "reverse_proxy" Internal HTTP/WebSocket proxy module Streams incoming client connections directly to your internal backend port.
upstreams[].dial Target address and port (e.g. localhost:3000) Tells Caddy where your local application process is listening.
terminal: true Stop evaluation flag Crucial! Once a request matches this domain, Caddy stops checking any subsequent routes in caddy.json. Without this, requests could fall through into other routes.

📋 5-Minute "Cold Start" Hosting Checklist

Follow these 4 steps anytime you spin up a new application:

1

Check Occupied Ports on the Server

Run npx caddy-cli -p /etc/caddy/caddy.json on the VPS to see what ports are taken. Pick an available port (e.g. 3000).

2

Generate Route Blueprint with caddy-template

Run npx caddy-template proxy yourdomain.keshavsoft.com 3000. This outputs the exact JSON block you need.

3

Insert into /etc/caddy/caddy.json

Paste the generated object into the apps.http.servers.srv0.routes array in /etc/caddy/caddy.json.

4

Reload Caddy with Zero Downtime

Run caddy reload --config /etc/caddy/caddy.json. Caddy immediately activates the new subdomain and issues an SSL certificate automatically!

🛠️ Gotchas & Troubleshooting

Gotcha 1: DNS A-Record Must Point to VPS IP First
Before Caddy can issue a Let's Encrypt / ZeroSSL TLS certificate, your DNS record (e.g. GoDaddy) for appointment.keshavsoft.com must point to your server IP (103.174.102.116). If DNS is not pointed, Caddy's ACME challenge will fail.
Gotcha 2: Always Include "terminal": true
If you omit "terminal": true, Caddy will keep processing subsequent routes even after matching the domain, which can cause 404 errors or route hijacking by catch-all rules.
Gotcha 3: Single Port WebSockets Need No Splitting
If your Node.js app attaches ws to the existing HTTP server instance (like appointment-notifier), you do NOT need ws-split. The standard proxy template handles both HTTP and WebSocket flawlessly!
